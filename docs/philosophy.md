# 设计哲学

本文汇集 AVM 的设计思想与决策依据。AVM 没有先例，本文按推理过程记录每个设计选择的目的，而不是先给结论。术语以 [CONTEXT.md](../CONTEXT.md) 为准；运行时的机制细节见 [docs/runtime.md](runtime.md)。

## 一、起源

2026 年 4 月，作者用三个 Agent 协作跑 auto research，不愿频繁切换、提示它们，于是写了 AVM。起点是观察：AI 对话的循环推进在形式上像 CPU 的指令循环（取指、解码、执行、写回），内容上却完全不同——AI 自己输出程序和指令，等待输入数据。

由于等待用户端输入指令很危险，不如在提示词里写好所有指令，封装成 kernel；用户指令输入到单独的 shell 对话，经分流系统分给不同对话处理。一个 AI 对话的行为因此是：自己输出程序和指令，等待输入数据。这就是 AVM 单个对话的行为。

## 二、核心命题：控制论与管理学取代软件工程

AVM 的根本洞见不是"把控制流从 Python 移到提示词"——那是表象。本质是：在 AVM 中，控制论和管理学代替了软件工程，成为构建系统的元学科。

传统 Agent 框架用软件工程方法：模块化、设计模式、接口、测试。AVM 放弃这些，用控制论原理（反馈回路、自适应、目标调节）和管理学思想（授权分权、职责边界、沟通协议）嵌入提示词中来组织计算。

- 提示词不是"指令"，而是**控制律**——设定参考目标、感知当前状态、比较偏差、执行调节动作。
- 提示词也不是"工作流脚本"，而是**组织管理手册**——谁负责什么、向谁汇报、哪些信息需要同步、异常如何处理。

提示词工程师写的是调节的律和组织手册，不是算法。这是范式替换，不是控制流的迁移。

## 三、中立基底：统一性来自协议，不来自 AI

AVM 运行时不管"你是谁"——LLM 可以发指令，Python 也可以发指令，双方是对等的执行单元。统一性来自**协议**（内存地址空间 + 指令集 + 设备总线），不来自 AI。

Core 只执行指令，不做业务决策。谁发起指令、谁执行指令，运行时不在乎。一个运行在 AVM 上的程序可以是纯 LLM 驱动的，可以是 Python 主导、在关键决策点调用 LLM 的，也可以是两者对等协作的。这与"Python 调 LLM"的框架范式根本不同。

## 四、对话作为进程，AVM 自己就是操作系统

线性上下文随轮数增长，回溯早期推论需要翻越长历史，信号衰减。进程树隔离上下文：每个对话有干净的任务边界，父只看子结论，深度增加不增加回溯成本。这是把操作系统的进程概念映射到 LLM 运行时。

AVM 自成体系，隔离于宿主操作系统、硬件、网络。对话是计算单元，休眠的对话就是被保存的计算状态——Core 信任它在计算间隙稳定保留。这是"虚拟机"假设：AVM 假设自己运行在稳定虚拟硬件上，而非可变、可崩、可插拔的软件宿主上。

生物学的同构：蛋白质、RNA、DNA 共同产生细胞的大部分核心功能，每个蛋白质都只是一个简单的机器，在全是蛋白质的环境里运转。把 LLM 塞进 Python 框架，就像把人造催化剂附着在框架上，再把蛋白质填进去——想要真正强大的 AI，不能用这种方法实现。

## 五、控制流在提示词里，数据即程序

提示词是文本，存放在内存中，可以被对话自身读写和修改——这提供了元编程和错误修复的物理基础。AVM 的选择不是"提示词还是代码"，而是控制流存放在哪一层。

这一选择的根是"数据即程序"：程序就是内存节点，扩展就是数据变化，因此不需要管理代码变化的插件机制。AVM 的扩展点在数据层，不在代码层；"软件更新"不是换插件，是写内存。

由此，一切 harness 与 context 工程都汇聚为提示词工程：AI 的行为就是另一些 AI 的 harness，AI 自己组装 AI 的 context。

**与 Lisp 的同与异**：Lisp 的 "code is data" 是语法层的统一（homoiconic）——代码和数据是同一个 s-表达式，抹掉区别以换取宏系统；AVM 的"程序是数据"是寻址层的统一——程序与普通数据是同一内存树里打了类型标（`ctrl.type`）的节点，保留区别。元程序员也不同：Lisp 的宏是同语言的确定性函数（编译期改写列表）；AVM 的"宏"是一个对话——Python 对话改写程序接近 Lisp 宏（确定性），LLM 对话改写程序则是概率性的，是 Lisp 没有的。所以 Lisp 换来语法抽象（宏、DSL），AVM 换来运行期自改与互改。AVM 没有语法层同像性，提示词文本不是可结构分解的 AST，因此没有 Lisp 式宏系统——它用寻址层 + 进程改写达到了"程序是数据"。

## 六、误差是调节，不是消除

软件工程假设：错误来自组件不正确，要在组合前用协议消除它。控制论假设：误差是系统的固有属性，无法消除，只能调节。

AVM 不做"消除奇怪"，它用隔离、调度、预算中断、capability 寻址把误差关在可控范围内，再用元编程和多样性把它转化为产能。代价与收益都来自同一个选择：把保证从"组合时"推迟到"运行时"。

## 七、简单内核，复杂度放在运行时

指令集固定且小（8 条）：加能力 = 开进程，不 = 加指令。Core 只保留最核心的对话推进、发送消息、创建对话，其余功能全部用内存读写实现。服务注册表是内存节点；设备化是便利与约束，不是本质。

进一步的设想是：让一个对话通过只读设备搜索另一个对话的上下文；需要更细的权限时，让对话直接互相通信提问，而不是在 Core 里加指令。权限的粒度由对话间的通信协商，而非由指令集枚举。

## 八、对话的偏见与多样性

AI 在一个上下文中倾向认为自己写的代码是好的（否则为什么要写？）。换一个新的 AI 看同一段代码，概率上倾向认为它是坏的（否则为什么被送到这里来？）。主对话"长就是好"的偏见会通过控制子对话而放大。因此每个对话只承担一件微小、可管理、可追溯的事——小而严格的任务边界是隔离上下文污染和 AI 自大偏见的物理手段。

AI 倾向于 AI 内容：AI 阅读包含 AI 生成文本的文档时，会抛弃人类写的内容，复述和解释 AI 的文字。对策是"随机集成增强"——打乱提示词顺序、减少句子、使用不同上下文、把输出分割成独立部分分发到不同对话，用多样性对抗概率模型的吸引子效应。

## 九、事件是中断，不是软件总线

AVM 的事件以硬件中断为原型，不是软件总线：对话注册监听对应中断向量注册，事件触发对应中断到达，休眠对话转就绪对应中断处理程序入队。

因为 AVM 假设宿主是稳定虚拟硬件，事件是瞬时的中断，不需要持久化、不需要重放、不需要恢复——那是软件宿主才需要的包袱。AVM 只需要中断模型这一半：事件体系，而非事件溯源体系。

## 十、环境主义

AVM 没有为 AI 做什么，只是提供一个本来就应该存在的环境：对话隔离与通信、内存共享与持久、程序安装与调度。它不预设任何进化机制，允许但不要求任何回路运行。

它没有意义，就像细胞外基质没有意义——不是一种发明，而是环境的还原。所有功能主义的提问方式（"AVM 解决了什么问题"）都问错了对象。

## 十一、未来方向

- **编译器**：把 skill、AI 应用、harness 通过一系列方法编译成 AVM 程序（一堆提示词、内存设备和 Python 程序）。
- **微架构**：顺序 ISA、乱序微架构——程序的语义严格顺序，调度器在底下并行。超标量与乱序执行是"把并发隐藏起来"的成熟哲学，从硬件搬给 LLM 运行时。
