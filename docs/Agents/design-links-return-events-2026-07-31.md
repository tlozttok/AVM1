# 设计决策：链接设备、返回工具、事件注册（取代 $/& 解引用）

**时间**: 2026-07-31
**状态**: 已确认（用户确认设计方向，代码未实现）
**背景**: 在验证对项目掌握度的讨论中，逐轮澄清了内存模型与对话调度语义。原 CONTEXT.md 声称"子对话结论自动回传父"，README 声称"`$MEM` 递归解引用 / `&` 单层解引用"，均与真实设计不符。
**起因**: 用户修正三个设计点：

1. **str 永远是 str**。`$` 递归解引用与 `&` 单层解引用删除——值不参与解引用。内存引入"符号链接"设计替代：链接是一个设备，主要用于遮盖真实内存路径（如 `$MEM.game.map.rooms` → `$rooms`），对话只看到别名、看不到真实路径，因此难以访问其他文件。这是 capability 边界的实现方式。
2. **子对话完成不唤醒父**。子对话（create_cmd）完成后结论回到父的 tool response 不是自动保证。新增返回工具，由子对话的 LLM 主动选择返回或不返回；工具调用后子对话立即终止（LLM API 规定一个工具调用只能有一个返回）。亚对话（create_sub）维持现状：完成即自动写回并唤醒父，紧耦合。
3. **回调注册是独立原语**。父对话显式注册自己的监听事件。VM 提供的事件源包括：子对话返回、定时、某个内存地址的更改、其他对话注册的自定义事件。事件触发后 core 将监听者从休眠转为就绪——这是对异步调度机制的模仿。组合事件、事件总线属于 AI 程序（提示词）的内容，不是虚拟机代码需要写的。

- 修订 CONTEXT.md：子对话定义、休眠定义、新增"链接"与"事件"术语、Capability 模型补充链接说明。

**影响**:
- 通信模型分两通道：返回工具只投递父（结论进父的 tool response / batch）；信号事件广播给所有监听者（子对话在返回前对预定义信号发出内容，其他对话通过监听获知）。
- 投递与唤醒不分离（2026-08-01 用户确认，按用户计划改动）：被调用方显式调用返回工具（`return_result`）后，Core 把结论写入调用者的 batch，并把调用者排到就绪队首（下一个被激活），不需要回调注册——消息已可用的对话不留在休眠队列。注意：返回必须由被调用方显式调用工具完成，不是自动或"直接"返回。
- 与现有代码的关系：`_on_conversation_finished` 非 sub 分支已实现"子完成不唤醒父"；`call_service` 的 caller_cid 回调机制是事件注册的雏形，新设计将其泛化为"监听者注册感兴趣的事件"。
- 待实现（需另行计划与审批）：LinkDevice（别名挂载、子路径委托、成环检测）、返回指令（终止语义 + 投递父）、事件注册表与事件分发（dormant → ready）、定时器、内存写入变更事件挂钩。

**废弃设计**: `$` 递归解引用、`&` 单层解引用。理由：内存已有符号链接设计后，不需要靠字符串前缀推断是否解引用；一个 str 就是一个 str。

## 返回工具协议与交互结束（2026-08-01 补充，按用户计划改动）

- **交互结束的终态**：对话返回不含指令的结果 = 交互结束，进入休眠（个体保留，等待事件/再次被调用）。"finished" 在 Core 中不存在，是概念态——记录被内核级关闭指令关闭的对话；关闭必须由对话自身或其他对话调用内核级关闭工具，且不需要被关闭对话的回应。
- **返回工具（`return_result`）协议**：被调用对话返回结果的唯一通道是显式工具。
  1. 子对话调用返回工具；
  2. Core 把结论投递给调用者的 batch（挂到原调用的 call_id），并把调用者排到就绪队首（确保它是下一个被激活的对话）；
  3. Core 给子对话写回确认"结果已发送"——LLM API 规定一次工具调用必须有一次返回（tool message）；
  4. 子对话下一回合以无工具的结果收尾 → 交互结束 → 进入休眠；
  5. 调用者被激活。
- 返回工具的唤醒适用于所有调用者（create_sub 的父、call_service 的调用者、create_cmd 的父），无需显式回调注册——前提是被调用方显式调用 `return_result` 工具。
- **call_service 改为工具返回**（按用户计划改动）：服务的自然结束不再自动写回/唤醒调用者，服务必须用 `return_result` 返回结果。`create_sub` 的紧耦合自动写回+唤醒父保持不变；亚对话若已用 `return_result` 显式返回，则收尾时不再自动写回（防重复投递）。

## create_cmd 简化与 ICC 路由（2026-08-02 补充，按用户计划改动）

- **create_cmd 去掉 `user_ref`**：只创建子对话（`system_ref` + `para_ref`），工具响应返回 cid（格式化字符串，如 `"Success created: cid=1"`）。父保持活跃、不休眠；子对话创建后进入休眠、等待指令。
- **新增传指令工具 `send_instruction(cid, content, wait)`**：按 cid 寻址（无需名字查找）。支持两种语义：`wait=true` 时父休眠等待返回（请求-响应）；`wait=false` 时父继续执行（单向投递，返回仍会进父的 batch，异步收信）。Core 记录 ICC 记录，并把指令投递给被调用方——投递的消息是 JSON 格式字符串（默认），含 `icc_id` 和 `content`，content 不强制 JSON。
- **ICC id 必选**：`return_result(content, icc_id)` 按 ICC 记录路由回发起者并唤醒它（若发起者等待）。无记录即错误（归入挂起中的错误处理机制）。icc_id 计划复用发起者那次工具调用自带的唯一 call_id。
- **父不再是默认接收者（废弃 parent 回退）**：创建关系不构成返回通道；AI 的思考不默认透露给其他 AI；子对话输出默认写入共享内存（`$MEM`），谁需要谁读。
- **create_sub 保持原样**：保留 `user_ref`，立即执行，完成自动写回并唤醒父（紧耦合；亚对话是父的控制延伸，功能上不可信）。
- **取代旧决定**：~~"create_cmd 的父进休眠队列"~~（绑定旧语义"创建即执行"，已废弃）；~~"return_result 的 parent 回退"~~（已废弃）。与现有代码的冲突（parent 回退、单槽 caller_cid、create_cmd 带 user_ref 且父休眠）均已标记，待实现。

## Python 对话与消息格式 v2（2026-08-04 设计确认，按用户计划改动）

- **Python 对话接口与各家 AI 厂商提供的 API 一致（兼容 OpenAI）**：输入 OpenAI 格式 messages 列表，输出 content + tool_calls，与真实 LLM 端点对等（用户纠正：不是"和 LMU 一样"，LMU 只是真实 API 的客户端适配器）。程序以 `type="python"` 节点存在内存中，Core 加载代码并实例化执行器。para 对 Python 对话意义减少，暂不管。
- **消息格式 v2**：投递消息为 JSON 字符串，字段 `from`、`to`、`icc_id`、`content`。`to` 是名字或名字列表；多播时每个目标建立一条独立 ICC 记录（各自可 return_result）。
- **名字身份**：名字不唯一；冲突时用 settingup 文件地址消歧（如 `MEM.math Analysis`）。带名字的对话必然来自 settingup 文件（create_cmd 创建），文件地址可作名字；亚对话（直接传提示词）没有名字。name 是信息不是元信息（不放 meta/ctrl，放节点数据）。
- **寻址职责划分**：`send_instruction` 只用 cid；名字↔cid 转换是内核（kernel）职责，不是 VM 职责——简单内核字符串匹配，复杂内核可支持 AI 匹配。VM 只按 cid / ICC 路由。

## 消息 v2 实施（2026-08-04，按用户计划改动）

- `send_instruction` / `call_service` 投递消息为 JSON 字符串：`from`、`to`、`icc_id`、`content`。`from`/`to` 由 Core 填身份：有名字用名字；无名字（亚对话）= 父身份 + 自身 cid（如 `init#1`）。
- `create_cmd` 从 settingup 节点的 name 数据字段（value.name，信息不是元信息）读取对话名字。
- 多播：`send_instruction` 的 cid 可为整数列表；每个目标一条独立 ICC 记录（icc_id = `call_id#i`）；消息的 `to` 为名字列表。
- **两种返回方式统一**（2026-08-04）：`send_instruction` / `call_service` 带 `return_mode` 参数（`tool` 默认 / `message`）。
  - `tool` 模式：返回为工具响应；多播时 `UserMessageBatch` 按 call_id 累积结构化段并物化为 JSON 数组（每条含 from/cid/icc_id/content，方便 Python 程序 json.loads 解读），一次工具调用只有一次返回；发起者在所有目标返回前休眠，最后一个返回到达时被唤醒。
  - `message` 模式：发送时给"已投递到 X"确认响应满足 API 配对；各目标返回以消息（user content，含 from/to/icc_id/content）投递；返回到达时唤醒休眠的发起者（wait=false 时发起者继续，返回异步累积进 batch）。
- 调度修正：发起者是否挂起由指令执行结果决定（成功投递/创建才置入休眠），不再由工具参数预先判定——失败的 send_instruction 不会把发起者挂起。
