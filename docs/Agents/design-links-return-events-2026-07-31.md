# 设计决策：链接设备、返回工具、事件注册（取代 $/& 解引用）

**时间**: 2026-07-31
**状态**: 已确认（用户确认设计方向，代码未实现）
**背景**: 在验证对项目掌握度的讨论中，逐轮澄清了内存模型与对话调度语义。原 CONTEXT.md 声称"子对话结论自动回传父"，README 声称"`$MEM` 递归解引用 / `&` 单层解引用"，均与真实设计不符。
**起因**: 用户修正三个设计点：

1. **str 永远是 str**。`$` 递归解引用与 `&` 单层解引用删除——值不参与解引用。内存引入"符号链接"设计替代：链接是一个设备，主要用于遮盖真实内存路径（如 `$MEM.game.map.rooms` → `$rooms`），对话只看到别名、看不到真实路径，因此难以访问其他文件。这是 capability 边界的实现方式。
2. **子对话完成不唤醒父**。子对话（create_cmd）完成后结论回到父的 tool response 不是自动保证。新增返回工具，由子对话的 LLM 主动选择返回或不返回；工具调用后子对话立即终止（LLM API 规定一个工具调用只能有一个返回）。亚对话（create_sub）维持现状：完成即自动写回并唤醒父，紧耦合。
3. **回调注册是独立原语**。父对话显式注册自己的监听事件。VM 提供的事件源包括：子对话返回、定时、某个内存地址的更改、其他对话注册的自定义事件。事件触发后 core 将监听者从休眠转为就绪——这是对异步调度机制的模仿。组合事件、事件总线属于 AI 程序（提示词）的内容，不是虚拟机代码需要写的。

**影响**:
- 通信模型分两通道：返回工具只投递父（结论进父的 tool response / batch）；信号事件广播给所有监听者（子对话在返回前对预定义信号发出内容，其他对话通过监听获知）。
- 投递与唤醒不分离（2026-08-01 用户确认，按用户计划改动）：返回工具投递结论即直接唤醒调用者（排到就绪队首），不需要回调注册——消息已可用的对话不留在休眠队列。
- 与现有代码的关系：`_on_conversation_finished` 非 sub 分支已实现"子完成不唤醒父"；`call_service` 的 caller_cid 回调机制是事件注册的雏形，新设计将其泛化为"监听者注册感兴趣的事件"。
- 待实现（需另行计划与审批）：LinkDevice（别名挂载、子路径委托、成环检测）、返回指令（终止语义 + 投递父）、事件注册表与事件分发（dormant → ready）、定时器、内存写入变更事件挂钩。

**废弃设计**: `$` 递归解引用、`&` 单层解引用。理由：内存已有符号链接设计后，不需要靠字符串前缀推断是否解引用；一个 str 就是一个 str。

## 返回工具协议与交互结束（2026-08-01 补充，按用户计划改动）

- **交互结束的终态**：对话返回不含指令的结果 = 交互结束，进入休眠（个体保留，等待事件/再次被调用）。"finished" 在 Core 中不存在，是概念态——记录被内核级关闭指令关闭的对话；关闭必须由对话自身或其他对话调用内核级关闭工具，且不需要被关闭对话的回应。
- **返回工具（`return_result`）协议**：被调用对话返回结果的唯一通道是显式工具。
  1. 子对话调用返回工具；
  2. Core 把结论投递给调用者的 batch（挂到原调用的 call_id），并把调用者排到就绪队首（确保它是下一个被激活的对话）；
  3. Core 给子对话写回确认"结果已发送"——LLM API 规定一次工具调用必须有一次返回（tool message）；
  4. 子对话下一回合以无工具的结果收尾 → 交互结束 → 进入休眠；
  5. 调用者被激活。
- 返回工具的直接唤醒适用于所有调用者（create_sub 的父、call_service 的调用者、create_cmd 的父），无需显式回调注册。
- **call_service 改为工具返回**（按用户计划改动）：服务的自然结束不再自动写回/唤醒调用者，服务必须用 `return_result` 返回结果。`create_sub` 的紧耦合自动写回+唤醒父保持不变；亚对话若已用 `return_result` 显式返回，则收尾时不再自动写回（防重复投递）。
