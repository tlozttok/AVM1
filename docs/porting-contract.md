# AVM 移植契约（Porting Contract）

本文是"把外部编排方案写成 AVM 软件"的交付约定。读者有两类：**执行者**（拿到契约去移植的人或 Agent）与**验收者**（安装、使用并判断是否保留它的宿主/操作员）。

契约不规定外部方案长什么样，只规定交付物的形状与验收方式。术语以 [CONTEXT.md](../CONTEXT.md) 为准；运行机制见 [docs/runtime.md](runtime.md)；程序写法见 [docs/programming-guide.md](programming-guide.md)；持久运行的机制见 [docs/runtime.md 的「持久运行」](runtime.md#持久运行重启恢复--回合日志)；包数据怎么进 AVM 见本文的「包数据怎么进 AVM」一节。

## 交付物

一次移植交付七样东西。缺任何一样，验收者都无法在不读代码的前提下判断它能不能用。VM 里没有"软件包"这个概念：包格式、安装位置、安装记录与版本指针都是 OS 的约定，不由运行时校验。

| # | 交付物 | 内容 | 验收方式 |
|---|---|---|---|
| 1 | 数据节点包 | 一段内存子树，节点用**显式节点格式**（`{kind, meta?, ctrl?, value}`）书写；清单文件是 OS 的约定，VM 不读 | 经只读包仓库设备读入后，被安装程序搬进 `$MEM` |
| 2 | 安装程序 | `plm.command` / `plm.python` 程序正文：读包仓库设备、按 OS 自己的分区把节点写进 `$MEM`，自己写安装记录与版本 | 自测里能跑通，重复运行结果确定 |
| 3 | 设备代码（按需） | `MemoryDevice` 子类；不发事件；错误信息不回显写入原文；按设备条目（`file` / `class` / `args`）另附 | 经宿主/操作员审批后由 `$MEM.device_loader` 的 `load_device` 挂载 |
| 4 | `README.md` | 做什么、怎么用、能力声明、已知退化 | 验收者只读它就能上手 |
| 5 | 保真度账本 | 一致 / 退化 / 未实现 三栏 | 每条退化有原因，能对照原方案核查 |
| 6 | 行为场景 | 输入序列 → 可观察输出，脚本化 | 自测里可重复跑 |
| 7 | 自测 | 用 MockLMU，`python -m pytest` 可跑 | 全绿，且不调真实 API |

数据节点包的最小形状（显式节点，无隐式转换）：

```json
{"kind": "dict", "value": {
  "programs": {"kind": "dict", "value": {}},
  "params": {"kind": "dict", "value": {}}}}
```

设备条目按镜像 `devices` 段的形状另附，`file` 相对设备条目所在目录：

```json
{"path": "io", "file": "io.py", "class": "EchoDevice", "args": {}}
```

## 包数据怎么进 AVM

一个可照抄的最小示例见 [packages/sysinfo](../packages/sysinfo/README.md)（数据节点包 + `plm.command` 安装程序 + 设备代码，含手动安装步骤）。

VM 只提供内存树、指令与设备。包怎么分发、装到哪里、装什么，由 OS 决定；下面三条是 **OS 侧约定**，不是 VM 的校验规则：

1. **接入**：base 镜像已带示例设备 `$MEM.pkgrepo`（`PackageRepoDevice`，`images/devices/pkg_repo.py`），只读，按现有 `MemoryDevice` 子类实现。向根地址写入一行相对路径装载，验证通过后读接口暴露包文件：

   ```text
   memory_write $MEM.pkgrepo "pkgs/demo"      # 空串或纯空白清除装载；失败保留旧包
   $MEM.pkgrepo.manifest                      # manifest.json 原文
   $MEM.pkgrepo.data                          # data.json 原文（显式节点，根为 dict）
   $MEM.pkgrepo.files                         # 每行：相对路径 字节 sha256
   $MEM.pkgrepo.read."devices/echo.py"        # 包内已列文件全文
   ```

   这个设备的包格式（`manifest.json` / `data.json` / 可选 `install.py` / 可选 `devices/*.py`）是 **OS 层约定**：设备按它验证路径与内容，VM 不校验、不理解；设备不 import/执行包里的 Python，也不写安装事务。
2. **搬运**：OS 的安装程序读仓库设备内容，按 OS 自己的分区约定用 `memory_make` / `memory_write` / `edit_metadata` 把节点搬到 `$MEM`，自己维护安装记录、版本指针、升级与回滚策略。
3. **设备代码**：宿主 Python 由宿主/操作员审批后挂载；`mount_device_entry` 在 import 前重算文件哈希并核对。base 镜像的 `$MEM.device_loader`（`load_device` 命令）是这条通道的示例入口，不是 VM 规定的唯一入口。

**VM 不校验包格式、不接受包路径、不写安装记录**：没有包文件校验、没有安装落点、没有版本指针。安装位置、是否保留 cid、升级/回滚、签名与依赖解析全归 OS。

## 硬约束

违反任何一条，交付即不合格。

1. **不改 `avm/`**：不加指令、不改事件类型、不改调度状态机、不改 `Core` 的行为。移植发生在镜像与程序层。
2. **不用未实现的能力**：`$time` / `$sleep` / `$random` 设备、整棵子树删除、运行期创建或改写链接、运行期注册 PLM、事件持久化与重放、定时器、中断优先级与屏蔽位、文件密码。需要这些的机制，在账本里记"未实现"，不要绕过。
3. **能力最小化**：程序节点用 `value.caps` 声明子对话的模式、根与工具集（见 [docs/capabilities.md](capabilities.md)），只申请做到这件事需要的部分。
4. **不调真实 API**：自测全部使用脚本化执行器（`tests/test_avm.py` 的 `MockLMU` 是参照）。真实行为由验收者负责。
5. **包约定归 OS**：交付物按三类内容组织（数据节点包 / 安装程序 / 设备代码）。VM 不校验包格式、不接受包路径、不写安装记录。自定义 PLM 是核级注册表，不随交付物分发；需要 Python 逻辑时写成 `plm.python` / `plm.command` 程序节点。
6. **版本号若作为内存键，不能含点号**（点号是路径分隔符），用 `1_0_0` 这样的形式；版本号的语义与放置位置由 OS 决定。
7. **跨轮状态落在 `$MEM`**：Python 程序的状态放在 `$MEM`，不要放在 PLM 命名空间变量里；恢复时命名空间会重建（见 [docs/programming-guide.md](programming-guide.md) 的「持久运行与跨轮状态」）。

## 怎么移植

1. **写机制清单，不写品牌。** 例如"监督者派活、工人回报、状态落黑板、完成唤醒下游"。逐条标：必须保真的、可以退化的、当前原语做不到的。
2. **逐条映射到 AVM 原语**，先只写落点，不写实现：

| 外部编排里的东西 | AVM 里的落点 |
|---|---|
| 角色 / 智能体 | 对话：LLM 用 `settingup` 程序，确定性逻辑用 `python` 程序 |
| 共享状态 / 黑板 | `$MEM` 子树；描述写给模型看，控制数据写给运行时看 |
| 消息 / 事件 | `send_instruction` 投递；`listen_event` + 处理器返回 `notify` |
| 工具 | 10 条指令 + PLM 程序 + 设备 |
| 工作流 / 图 | 对话链（`create_sub` 同步链）或事件驱动（监听 + 唤醒） |
| 派生执行者 | `create_sub` 紧耦合、用完即删；`create_cmd` 独立个体、休眠等指令 |
| 人机审批 | `$inputs` / `$outputs` 设备 + 一个等待节点 |
| 运行日志 | 监测帧与 `$MEM.monitor` |

3. **先跑最小链路**：一个对话 + 一次投递 + 一次等待 + 一次结果落盘。链路通了再扩角色与分支。
4. **写账本与场景**。账本按机制逐条写，不按目录结构写；场景给输入与可观察输出，不写内部状态。
5. **自测绿了再交付**，并在 `README.md` 里写清"装好之后应当看到什么"。

## 能力声明

`README.md` 里必须有一节，列出这套软件会碰什么：

```text
模式：用户态 / 内核态
根：pkg（软件自己的子树）、mem（如需要读全局状态）
工具：memory_read, memory_write, create_cmd, send_instruction, listen_event
创建对话：是（LLM / Python）
设备：io（读写软件子树里的路径）
外部副作用：无
```

验收者据此判断是否安装。没有这一节，安装时无法评估。

## 验收

**交付前（执行者）**：

```bash
python -m pytest <交付目录或 tests/ 下的自测> -q    # 全绿
```

自测至少覆盖：设备读到的数据能搬进 `$MEM`、安装程序重复运行结果确定、场景按顺序跑通、按 OS 自己的约定卸载/清理后路径不可用。

**交付后（验收者）**：

1. 在暂存分区安装（先装再决定，不直接进主系统）；
2. 按 `README.md` 跑一遍场景，对照"应当看到什么"；
3. 对照能力声明，确认没有超出预期的访问；
4. 通过则提升为正式软件，不通过则移除并记录原因。

判据三条：不改交付物就能用；实际能力与声明一致；账本里的退化项可以接受。

## 常见错误

- **表面移植**：把原方案的流程图翻译成对话链，顺手把关键机制改成好实现的形态，账本里却写"一致"。例如"父创建子后继续执行、不等待"被写成"父等子返回"。
- **能力过宽**：为了好写，给程序申请 `$MEM` 根和全部工具。安装者无法判断边界。
- **用未实现特性**：写了 `$sleep` 或在提示词里要求链接换向，自测因为没执行到而变绿。
- **拿亚对话做 Agentic 任务执行**：[CONTEXT.md](../CONTEXT.md) 对亚对话的定性是紧耦合、不可信；父是 AI 对话时它只能用于省 token，AI 父把任务交给亚对话会放大过度附合/过度批判。父是确定性工作流（如 Python 程序）、亚对话用完即抛时不属于此列，可以用亚对话正常执行任务，但要在账本里写明父是确定性程序、system 提示词由程序生成。
- **把安装写成 VM 机制**：要求运行时校验包格式、记录安装事务或维护版本指针。VM 没有这些概念，安装是 OS 程序读设备、写 `$MEM` 的事。
- **版本号带点**：版本号写进 `$MEM` 当键时不能含点号；`1.0.0` 建得出来但读不回来。
- **Python 状态放命名空间**：自测能过，恢复后状态丢失。
- **设备发事件或回显内容**：装载类设备一旦发事件，写入内容会出现在事件载荷里。

## 交付与版本

- 文件放一起：数据节点包目录、安装程序节点正文、设备文件、`README.md`、账本、场景、自测。
- 包格式与版本字段是 OS 自己的约定，VM 不读；把版本写进 `$MEM` 键时不能含点号。
- 升级/回滚由 OS 的安装程序与分区约定实现；VM 不提供版本指针。
- 交付时说明它依赖镜像的哪些前提（例如需要镜像挂的只读包仓库设备（base 的 `$MEM.pkgrepo`）、需要 `$MEM.device_loader` 之类的设备装载入口、需要某个 PLM 类型）。

## 讨论区

- 能力声明目前只有 README 里的文字，没有机器可读字段；是否给交付物加一个 `caps` 段，等第一批移植之后再定。
- 保真度目前是文字账本，没有统一评分；是否需要一份可比较的评分表，取决于移植数量。
- 自定义 PLM 不能随交付物分发；如果某些方案强依赖自定义执行器，要另议。
- 暂存区与"先在独立 AVM 实例里试跑"的流程还没固化，目前靠验收者手动做。
