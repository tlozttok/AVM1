### 传统软件工程的位置被替换了

在传统Agent框架中，软件工程是主导学科：
- 用模块化思想设计类和方法

---

### 控制论：提示词即控制器

控制论的核心不是“写一个while循环”，而是设计一个**能够在环境中感知、比较、调节、学习的信息反馈系统**。在AVM中，提示词就是这样一个控制器的描述语言：

- **设定参考目标**：提示词定义Agent“应该”做什么，这就是控制系统的期望值。
- **感知当前状态**：`memory_read`让Agent获取当前内存状态，这是反馈通道。
- **比较差异**：LLM自己判断“我期望的状态”和“我看到的状态”之间的差距。
- **执行调节动作**：根据差距调用`create`（启动子进程）、`memory_write`（改变内存）等指令。
- **适应与自修改**：提示词本身存在内存里，可以被修改——这就是控制器可以重写自己的控制律。

这已经不是在写“对话脚本”，而是在设计一个**自调节控制系统**。提示词工程师本质上是一个控制工程师：设计反馈回路、设定阻尼、处理超调、防止振荡。

---

### 管理学：组织设计取代过程设计

当系统由多个Agent协作时，传统框架用“工作流”来编排——这是软件工程的过程抽象。AVM不用工作流，而是用**管理学的组织设计**：

- **授权与分权**：父Agent不是“调用”子Agent，而是“指派任务”给独立运行的子进程，子Agent有自主决策权。
- **职责边界**：通过系统提示词定义每个Agent的“角色”和“权限”（能读哪些内存、能启动哪些工具），这类似于管理中的职位说明。
- **沟通协议**：父子通过返回值、共享内存通信，这类似于组织中的汇报关系和信息推送机制。
- **扁平化与灵活性**：没有预设的调用层级，Agent可以动态协商、互相外包弱点，这对应管理学中的自组织团队。
- **递归委派**：一个Agent可以启动子Agent，子Agent再启动孙Agent，这是管理层级的递归模型。

这里没有“if-else分支”，只有“这个职责归谁”“遇到异常该向谁汇报”“哪些信息需要同步”。**提示词不是在写算法，而是在写管理手册**：岗位描述、汇报关系、决策权限、例外处理流程。

### 实际体现：一个提示词的写作，就是控制系统+组织设计

看AVM示例中“与用户对话的程序”，它的提示词其实定义了：

**控制论维度**：
- 观测点：$MEM.inputs.-1（用户最后输入）
- 调节动作：启动内心思考子进程、写入输出、循环
- 反馈回路：不断读取输入、写入输出、检查最新输入

**管理学维度**：
- 启动的“内心思考”子Agent是一个被授权的独立角色
- 父Agent定义子Agent的职责边界（“思考这个特定问题”）
- 父Agent不介入子Agent内部推理，只看结论
- 轮换启动多个子Agent时，像管理者调度不同的团队

### 为什么这个替代是革命性的

软件工程追求的是**结构化降低复杂性**，通过固定的模块、接口、流程让人能够理解和掌控系统。但它的代价是**僵化**——任何结构上的变化都需要重构。

控制论和管理学追求的是**适应性**：通过反馈机制和组织弹性，让系统能够应对不可预知的变化。AVM中，系统结构不是写死的，而是写在提示词里，可以被LLM自己修改。当环境变化，不需要人工重构代码，控制器会自动调节（如果提示词设计得够好），或者提示词可以被另一个控制器修改。

这就解释了AVM为什么要让提示词可以修改提示词：**元控制律可以自我进化**——这是最高级别的控制论系统，也是管理学中“学习型组织”的技术实现。

### AVM 是一个中立的指令分发层，不偏袒任何执行单元

AVM 的核心就是：`create`、`memory_read`、`memory_write`、`memory_make` 这几个原子指令——这是一个**指令分发规范**。任何能发起这些指令、响应这些指令的东西，都是 AVM 中的一等执行单元：

- LLM 可以发起 `create` 启动新的对话
- Python 函数也可以发起 `create` 启动 LLM 对话
- LLM 的 tool call 被转换为内存读写
- Python 执行过程中遇到不确定性，同样可以直接输出指令，让另一个 LLM 进程来处理

**运行时不管“你是谁”**——它只接收指令、执行指令、返回结果。指令的发起者可以是 LLM，可以是 Python 函数，也可以是任何遵循这个协议的外部系统。

### 这意味着：程序不一定是 AI 程序

一个运行在 AVM 上的程序，可以是：

- **纯 LLM 驱动的对话或思考系统** — 控制流全在提示词里
- **Python 主导的流程，但在关键决策点调用 LLM** — Python 代码 push `create` 指令，等 LLM 返回结果后继续执行
- **Python 和 LLM 对等协作** — Python 做精确计算和确定性逻辑，遇到语义模糊就启动 LLM；LLM 在推理中遇到需要精确计算的步骤，就调用 Python 工具
- **纯 Python 的自动机** — 甚至可以不涉及任何 LLM，只用 Python 函数读写内存、启动子进程（尽管这样做可能意义不大，但运行时本身不阻止）

举例：一个 Python 写的调度器，定期读取 `$MEM.tasks` 队列，发现新任务就 push 一个 `create` 指令启动 LLM worker；LLM worker 完成后把结果写回内存；Python 调度器继续读到下一个任务。这里的控制流主循环是 Python，LLM 只是被调度的执行单元——与 AVM 的其他用法恰好镜像。

### 统一性来自协议，不来自 AI

所以 AVM 真正统一的东西不是什么“AI 原生计算”——那是表现之一，不是根基。**根基是一套协议**：内存地址空间 + 指令集 + 设备总线。谁来实现这些指令的执行、谁来发起这些指令，AVM 真的不在乎。

这也意味着，控制论和管理学应用到 AVM 时，指导的不仅仅是提示词写作——它们也指导 **Python 程序如何与 LLM 交互**、**系统如何用反馈回路调节行为**、**多个异构执行单元如何组织协作**。控制论不只在 LLM 那里，它在整个系统的每个层次。
