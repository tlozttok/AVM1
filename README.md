# AVM — 以 LLM 推理为原始计算单元的运行时

AVM 是一个运行时：以 LLM 推理为最小可调度计算单元，程序以自然语言（提示词）的形式存放在内存中，由 AVM 负责调度和执行。

AVM 不是 Agent 框架。它不预设编排模式，不提供业务提示词，不与操作系统、硬件或网络直接交互。AVM 提供一套指令集、一个内存系统、一个调度器，以及把三者组合成"系统镜像"的格式。

术语以 [CONTEXT.md](CONTEXT.md) 为准，本文档不再重复展开。

## 事实

### 计算模型

对话（Conversation）是最小可调度单元：由系统提示词和用户提示词启动，循环执行 LLM 推理 → 指令执行 → 结果返回，直到返回不含指令的结果（交互结束）。

指令集（Core 只执行指令，不做业务决策）：

| 指令 | 作用 |
|---|---|
| `memory_read` / `memory_write` / `memory_make` | 读写内存、创建地址 |
| `create_cmd` / `create_sub` | 创建子对话 / 亚对话 |
| `register_service` / `call_service` / `transfer_service` | 注册、调用、移交服务 |
| `return_result` | 将结论显式返回给调用者 |

内存是全局键值树，三种数据类型：MetaDict、MetaList、str。str 永远是 str，不参与解引用。MetaDict / MetaList 带双元数据：元数据一给 LLM（快速扫描的描述），元数据二给 Core（type、signature 等结构化控制信息）。链接（Link）是设备：把真实路径挂载为别名，对话只看到别名、看不到真实路径（capability 边界）。

调度：对话处于活跃 / 休眠 / 就绪三态，同时只有一个活跃对话。交互结束进入休眠（个体保留，等待事件或再次被调用）；"finished" 是概念态，只记录被内核级关闭指令关闭的对话。调用关系：

- 子对话（create_cmd）：父休眠；子完成不唤醒父；结论由 `return_result` 显式返回并直接唤醒调用者。
- 亚对话（create_sub）：完成自动写回结果并唤醒父（紧耦合）。
- 服务（call_service）：调用者休眠，服务用 `return_result` 返回；服务交互结束后仍保持注册。
- 移交（transfer_service）：移交控制权，调用者不等待返回。

系统镜像：一个 JSON 文件 + 若干设备 Python 文件 = 一个标准 AVM 系统镜像（规范见 [docs/system-image.md](docs/system-image.md)）。镜像声明内存树、模型参数（para）、设备挂载、init 对话和可选持久化路径。

### 快速开始

```bash
pip install openai python-dotenv pytest
echo "OPENAI_API_KEY=sk-..." > .env

python -m pytest                        # 全部测试（MockLMU，不调真实 API）
python main.py                          # 读取 debug.json，加载镜像并运行
python main.py <image.json> --frames    # 运行后打印监测帧摘要
```

调试参数写在 `debug.json`（image / frames / transcript），不需要改命令行。示例镜像见 `images/demo.json`。

## 决策与动机

这个项目没有先例，每个设计选择都有具体动机。以下按推理过程记录，而不是先给结论。

### 控制流放在提示词里

现有框架用 Python 写控制流，LLM 只是被调用的函数。控制流写成代码后，改一种协作模式就要改程序。提示词是文本，存放在内存中，可以被对话自身读写和修改——这提供了元编程和错误修复的物理基础。AVM 的选择不是"提示词还是代码"，而是控制流存放在哪一层。

### 对话作为进程

线性上下文随轮数增长，回溯早期推论需要翻越长历史，信号衰减。进程树隔离上下文：每个对话有干净的任务边界，父只看子结论，深度增加不增加回溯成本。这是把操作系统的进程概念映射到 LLM 运行时。

### 子对话与亚对话的唤醒差别

两类协作的紧耦合程度不同。亚对话是父的控制延伸，父需要它继续，所以完成即唤醒、结果自动写回。子对话是独立执行单元，只对 AVM 整体内存的目的负责；父创建子后它的职责只是分发，子完成不构成父的唤醒事件。父要恢复，靠 `return_result` 投递的消息（直接唤醒）或注册的事件。

### str 永远是 str，链接是设备

如果字符串值可能被当作引用解引用，存储内容和读取结果就不一致，间接层不可控。链接是显式设备：别名挂载、子路径委托、成环检测，同时承担能力边界——对话只拿到别名，拿不到真实路径，就不能访问兄弟节点。

### 返回用显式工具

LLM API 规定一次工具调用必须有一次返回。如果结论回传依赖"对话恰好以正确形式自然结束"，结果不确定：LLM 总是输出内容，但不一定输出工具。`return_result` 把返回变成显式动作，由子对话决定返回或不返回。调用后子对话收到确认，下一轮以无工具结果收尾进入休眠，调用者成为下一个被激活的对话。

### 交互结束进入休眠

"结束"有两种含义：交互结束（一轮执行完毕）和个体结束（被关闭）。交互结束后对话个体仍存在，之后可被再次调用或事件唤醒，所以终态是休眠。这与异步调度一致：挂起的调用者不在可运行队列里，事件到来才回到就绪。

### 错误面向运行者

工具调用参数解析失败、未知工具名，不喂回给 LLM 让它自纠，而是输出到 stderr 给运行者。调试期系统错误需要人看见，LLM 自纠会掩盖运行时缺陷。

### 镜像格式显式

镜像要精确复现系统状态。隐式转换（"JSON 自动转成内存类型"）省事但不可控：类型、元数据、para 的识别都靠猜。显式节点（kind / meta / ctrl / value）让镜像每个字段有确定含义，代价是冗长。调试程序值得这个代价。

### 内存用双元数据

LLM 上下文有限，大文件不能整体塞入。元数据一给 LLM 快速扫描（描述 + 键列表），深入访问才展开子节点；元数据二给 Core / 内核态（type、signature），控制程序如何被解释。这是控制 LLM 视野的手段。

## 当前状态

已实现：指令集（9 个）、内存树与持久化、调度状态机、return_result 协议、监测器（帧 / 轨迹 / diff / 全文文件）、系统镜像加载（main.py / debug.json / persist_to）。

设计中（未实现）：内核态 / 用户态分离、事件注册与分发（定时、内存变更、自定义信号）、内核级关闭指令、Python 程序对等执行、链接设备、文件密码与访问回调。
