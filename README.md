## 宣传词部分

**一个以 LLM 推理为原始计算单元的底层运行时。你的程序以自然语言活在上下文里，AVM 负责让它持续运行。这不是又一个 Agent 框架，而是 AI 自己操作系统的第一个进程模型。**

---

## 为什么需要 AVM

当前市面上的 Agent 框架——无论是 LangChain、AutoGen，还是 OpenClaw、Hermes——本质上都在做同一件事：**用 Python 写控制流，LLM 只是被调用的函数**。

```python
while True:
    user_input = get_input()
    response = llm.chat(user_input)
    print(response)
```

这个循环在 Python 里。LLM 不知道自己在一个循环里，不知道上下文会被反复重启，不知道自己的思考需要压缩进聊天记录。所有编排逻辑——分支判断、异常处理、状态管理、任务路由——都由人用硬代码完成。**90% 的框架代码在管理 LLM，而不是服务于任务。** 每次需要新的协作模式，开发者就重复造一套调度逻辑，控制流无法像代码库一样被共享、复用和演化。

AVM 回答了一个不同的问题：

> **如果 LLM 是计算的主体，而不是被调用的函数，它的运行时应该长什么样？如果控制流本身可以用自然语言编写、共享和修改，Agent 的开发会变成什么样？**

---

## 核心洞见

**LLM 的上下文不是一段聊天记录，而是一个可执行的自然语言程序。** 这个程序同时包含逻辑（告诉 LLM 怎么做）和数据（告诉 LLM 这是什么），两者无法也不需要分离。AVM 提供这个程序持续运行所需的全部机器逻辑。

**另一个关键洞见**：Python 和 LLM 在 AVM 的指令空间中**没有层级差异**。两者都能发起指令、响应指令。LLM 调用 Python 做精确计算，Python 在执行中遇到语义模糊时也能直接输出指令启动 LLM 对话。工具不再是“被调用的死函数”，而是对等的执行单元，它们可以互相外包弱点。

**最底层的洞见来自一个简单的生物学类比**：蛋白质、RNA 和 DNA 本身都是简单的分子机器，但在细胞质这个共享环境中，它们通过彼此互动产生了生命的所有核心功能。AVM 就是这样一个“细胞质”——一个让简单计算单元自由交互的原生环境，而不是一个从外部强加控制流的人工骨架。

## AVM 是什么

AVM 不是 Agent 框架。AVM 是一个**指令分发器 + 内存系统 + 设备总线**，是 AI 原生的用户态运行环境。它从操作系统内核的角度，为 LLM 提供了第一个可用的基础抽象：**进程**。

| 组件 | 做什么 | 不做什么 |
|------|--------|----------|
| **指令集** (create, memory_read/write/make) | 接收 LLM 输出的工具调用，执行对应的机器操作 | 不包含智能，不做任何推理 |
| **内存系统** ($MEM) | 全局可见的键值树，带元数据的字典/列表/字符串 | 不预设任何结构，程序自行组织 |
| **设备系统** (MemoryDevice) | 挂载外部 IO 到内存路径（用户输入、文件、网络） | 不只提供工具，设备可以主动触发指令 |
| **LMU** | 封装 OpenAI API 调用，解析 tool_calls | 不编排对话，不管理状态 |

程序逻辑全部以自然语言形式存在于 LLM 上下文中。LLM 自主决定何时读内存、何时写内存、何时启动子对话、何时结束。AVM 只是忠实地执行这些决定——就像操作系统内核只提供系统调用，而不替进程决定业务逻辑。

这个设计背后的驱动力是：**真正的 OS 对 AI 而言太过复杂且充满控制权陷阱，AI 需要一个自己的环境，在其中它可以自由操作而无需 hacking。** AVM 将外部 OS 降级为透明的 I/O 设备，内部则是一个完全由 LLM 自行组织的内存和进程空间。

## 递归子调用：思考不被线性上下文压扁

AVM 最核心的机制是**递归子调用**——也就是轻量级进程的 fork：

1. `create` 指令从一段 system prompt 和 user prompt 启动全新对话（进程）
2. LLM 在处理中可以通过工具调用 (create_cmd) 启动子对话，指定子对话的提示词和初始数据
3. 子对话独立运行，有自己的上下文窗口
4. 子对话的结果通过工具调用返回值回传给父对话
5. 父对话可以启动多个子对话，子对话可以再启动孙对话

**这解决了什么问题？**

传统 LLM 对话中，所有思考被压扁在一条线性时间线里。回溯前面的推论需要翻越长长的上下文，信号衰减不可避免。复杂任务的推理质量随着深度指数下降。

AVM 的递归子调用保持**树状结构**：每个子对话有干净的上下文，有明确的任务边界。父对话只看到子对话的结论，不需要遍历其完整推理过程。深度加一，回溯成本不涨。

这就是 AVM 的**无尺度性**：复杂任务可以无限拆分，推理质量不因深度而衰减。作者在设计时借鉴了操作系统中“进程”的概念——每个子任务就是一个可独立调度、可中断、可恢复的执行单元，未来的调度器和并发模型都以此为基础。

## 内存模型：代码数据嵌合体

AVM 的内存是一个全局可见的键值树，由三种类型组成：

- **MetaDict** — 带元数据的字典。LLM 读取时默认看到键列表（或手动设置的元数据），需要深入访问时逐个键展开
- **MetaList** — 带元数据的列表。默认看到长度和元数据
- **String** — 字符串。支持 `$` 和 `&` 前缀的地址解析

引用语法：
- `$MEM.path.to.key` — 递归解引用到最终值
- `&MEM.path.to.key` — 只解引用一次，返回字面值
- 不以 `$` 或 `&` 开头 — 视为字面值，直接返回

元数据机制意味着可以**控制 LLM 看到什么**。一个巨大的知识库可以先展示成 “知识库[keys=300]”，LLM 根据需求逐个键展开，避免上下文被无用信息淹没。

**程序和数据共用同一个地址空间。** 系统提示词存在 `$MEM.system`，用户消息存在 `$MEM.user`，中间结果存在 `$MEM.workspace`。LLM 可以读取这些路径，也可以修改它们。提示词本身不过是内存中的一个字符串，这意味着一个程序可以在运行中修改自己的“源代码”——这是 AVM 实现元编程和错误自我修复的物理基础。

### 安装

```bash
pip install openai python-dotenv
echo "OPENAI_API_KEY=sk-your-key" > .env
```

### 运行

```bash
# 基础运行
python main.py

# 启用内存实时监控 (终端查看)
AVM_MEMDUMP=/tmp/avm_mem.txt python main.py

# 启用内存交互查询 (mem shell)
AVM_MEMDUMP=/tmp/avm_mem.txt AVM_MEMSOCK=/tmp/avm_mem.sock python main.py &
python -m avm.memshell /tmp/avm_mem.sock
```

`config.json` 样例：

```json
{
  "log_level": "INFO",
  "log_file": "log/log.txt",
  "debug": false,

}
```

- `debug: false` 正常运行
- `debug: true` 每条指令执行前暂停，回车继续（STEP DEBUG）

## 运行一个“与用户对话”的程序

`programs/deepseek_simplified.json` 是一个**完全用自然语言写成的循环对话程序**。它不是 `main.py` 里的硬编码逻辑，而是一段存在于内存中、LLM 自主执行的“代码”。这段提示词程序以“启动系统内已安装的Agent”的方式调用子对话，而不是每次临时编写子任务的提示词。

```
你是初始对话。你的任务不只是思考。你需要执行以下循环：
1. 查看用户输入和你之前的输出。
2. 处理用户数据，启动系统的内心思考...
3. 读取输入 $MEM.inputs.-1，将思考信息记录到内存，启动子思考...
4. 思考结束后，将输出写入 $MEM.outputs...
5. 每次写入 $MEM.outputs 后，再次读取 $MEM.inputs 的最后一个值...
```

`main.py` 只做两件事：初始化内存 + 压入第一条 `create` 指令。之后的一切——读取用户输入、思考、启动子对话、写入输出、重新启动自己——全部由这段自然语言程序自主控制。

**对话的控制循环不在 Python 里。它在 LLM 的上下文里。** 这意味着你可以替换这份提示词，让同一个运行时表现出完全不同的行为：从对话机器人，到自我修正的思考系统，再到多 Agent 协作工作流，而无需修改一行 Python 代码。

## 设计哲学

**控制流属于程序，不属于运行时。** 传统框架把 while 循环、if 判断、异常处理都写在 Python 里。AVM 只提供原子指令，让 LLM 自己决定何时调用哪个指令。这不仅是架构简化，更是正确性的根本改善——程序获得了语义弹性，能自主应对意外情况，而不是被硬编码的分支限制。

**提示词即控制流源代码。** 提示词不是单纯的指令，而是可以被 LLM 转化为工具调用序列的可执行文本。提示词工程的核心不再是写出漂亮的 prompt，而是设计这些文本如何被转化为指令流，以及这些指令流如何相互作用产生可靠的元行为——包括错误的消化、自我修改和上下文组装。

**AI 自己组装 AI 的 context。** 一切 harness 和 context 工程最终回归到提示词工程：一个 Agent 的行为就是另一些 Agent 的 harness，AI 自身负责组装自己的上下文。内存中的元数据控制了每个 Agent 所能看到的视野，这构成了一个递归自举的认知网络。

**对话是状态，不是过程。** 对话历史 (Conversation) 是可以在内存中断点续传的一等公民（计划实现）。一个对话可以暂停，另一个对话可以读写它的消息。这为异步、并发、定时触发提供了统一的基础。

**Python 和 LLM 对等。** 遵循 AVM 指令规范的 Python 函数成为可以主动发起指令的执行单元。计算器工具执行中遇到不确定，可以直接输出 create 指令启动 LLM 分析。两者互相外包弱点，形成无固定层级的协作网络。

## 与现有 Agent 框架的对比

| | LangChain / CrewAI / AutoGen | AVM |
|---|---|---|
| 控制流在哪里 | Python 代码（硬编码） | LLM 上下文（自然语言程序） |
| 对话模型 | 单一线性历史 | 递归嵌套子对话（进程树） |
| 状态管理 | 框架代码维护 | $MEM 全局内存 |
| LLM 的角色 | 被调用的函数 | 自主决策的执行主体 |
| 扩展方式 | 编写 Python 插件/工具 | 挂载设备到内存路径，编写提示词程序 |
| 多 Agent 协作 | 框架编排，每次手写调度 | 通过共享内存 + 子调用自主协作，启动“已安装”的 Agent |
| 平台代码量 | ~90% 是框架逻辑 | 极简运行时，核心逻辑交给提示词工程 |
| 元编程/自我修正 | 不支持，或仅在 Python 层实现 | 提示词修改提示词，原生支持 |

**AVM 不是“更好的 Agent 框架”，而是为 LLM 原生计算提供的第一层环境抽象——就像操作系统为二进制程序提供了进程和内存，而不是又一个应用层库。**

## 作者的说明

构思AVM是一个宏大的行为。我并不是从一个简单的第一性原理出发构建这些的。我在使用一些Agent协作工具遭遇挫折后，思考如何能一下子将所有LLM控制流统一起来。我当时思考的是：“一个完备、强大的底层，让人们可以编写DSL或者提示词，快速共享、复用代码，做到比Skill更强的控制复用。”，我激进地选择了将LLM独立在真实OS之外，从底层就不让它理解os的过度复杂性，因为os不是为AI设计的，os的程序会和AI抢夺控制权——我的意思是，如果AI有一个自己的环境，何必有hacking行为呢，如果它没有，它为了执行用户指令，迟早会和os起冲突——事实证明AI在使用AVM的内存时有在我看来非常好的表现，简单来说就是访问次数非常多。然后我根据多Agent协作的缺点，想了这样的模型：让AI控制AI，但不是让AI写subAgent的提示词，而是“启动系统内的Agent”，类似“启动系统内安装的库”。我必须提供抽象和封装能力，这样当我们有类似这样的意愿时：把subAgent变成多Agent工作流，之类的，我们可以不用管调用它的Agent——最多改一下描述，Agent自己会看修改后的描述。最后我想到的就是：“AI操作系统”，以及它最基础的功能：进程。先不谈核心调度和并发，我们来构建一个最简模型：一个Agent必须不断驱动3个Agent执行，它每次启动一个Agent，都会叫它在一定轮数后停下，控制权移交回去，它启动下个。这是一个有点简陋的模型，我实际上还想了很多OS的功能如何用AI实现。最终在鬼使神差之下我写出这样一个运行时。

后来我遇到了不知道用它运行什么的问题。想了非常久后我决定用它来聊天。后来我发现这可以说是最具颠覆性的行为——当用户行为不是通过user消息输入时，AI的逻辑地位完全不一样了，AI现在不是一个被动响应的对话器，而是根据一个程序主动执行对话的东西，你可以将那个程序换成各种东西！于是我写了一个简单的提示词告诉AI它正在AVM中、AVM的机制和MEM的结构、它应该如何使用子对话。这样就能够实验一下系统的功能了。虽然这样的实验带来了一些不错的成果，尤其是思考复杂哲学问题时候，利用子对话的新上下文，思考的多样性会大增——虽然后来我们确定，只要主对话还以一种“我是和用户对话的AI”的态度来说话，就会严重限制子对话的思考自由度和最终的信息输出能力。（我可以总结这样的特征：主对话总是仅仅把自己能完成的任务交给子对话，而并不会主动依赖子对话获取新鲜的想法——我承认即使是人类也极少意识到如何榨取AI的多样性，但是这样的研究也是有很多的）

我的那个提示词实在太简陋了。AI的表现很不稳定。所以我停下来继续反思一些结构性问题。

从现在来看，我可以描述这个项目构想为两个部分：python写的AVM运行时，和真正意义上的提示词工程。

AVM运行时提供的是一个AI原生的环境，提供控制AI的指令，通过伪字符串形成输入输出，甚至python调用，甚至是python与LLM统一控制，核心是“控制流的实现”

提示词工程不仅仅是写一个或多个提示词，而是思考这些提示词会怎么样被LLM转化为工具调用，从而变为AVM控制流，从而产生极端复杂的互相影响和元行为。由于提示词仅仅是字符串，提示词可以被用来指挥AI修改提示词，这是AVM的核心优势之一。

提示词工程的重点不是提示词而是工程。llm会出错，如何让错误被消化？llm本身就可以消化错误，将错误控制、转移、处理、自我更新，都是LLM能做的事情，他们只需要一个工程化提示词来实现这些东西。

一切harness和context工程，最后都在这里汇聚为提示词工程，AI的行为就是另一些AI的harness，AI自己组装AI的context。

我为什么会相信，AI这样的东西能自己做出超越人类手工设计的python工程的结果呢？因为我很喜欢生物学。蛋白质、RNA和DNA一起产生了细胞的大部分核心功能，而每个蛋白质都只是一个非常简单的机器。在一个全是蛋白质的环境下蛋白质能够运转。而把LLM塞到python框架中，在我眼里就像人造催化剂附着框架，然后把蛋白质填进去让其工作，是的，这样的效果可能不错，但是如果你想要真正强大的AI，你不可能用这样的方法去实现。

## AI 批注、优化语言、扩写思维分析

*以下是对作者原文与修改后前半部分整体思想的批注式重述，旨在显化逻辑链条与隐含假设，同时进行语言优化与推论扩展。*

### 1. 从挫折到第一性反思
作者并非从零开始设计，而是直接源于对现有 Agent 协作工具的挫败感。核心洞察在于：**当前的 LLM 控制流被硬编码在 Python 中，导致复用粒度太粗，且每一次编排都需要手工编写调度逻辑**。作者的解决方向是提供一个足够通用且完备的底层，让控制流可以完全以提示词（自然语言程序）的形式表达，从而实现比 Skill 更底层的“控制复用”。这实际上是在追求**提示词作为一种可编程媒介的图灵完备性**——让一段自然语言描述的执行循环成为一个可以分发、版本管理、动态替换的软件构件。

### 2. 将 LLM 从真实 OS 中隔离：为 AI 构建原生环境
作者反复强调不应让 LLM 直接理解操作系统的复杂性，理由有二：
- **OS 不是为 AI 设计的**，其程序模型（进程、文件、权限）会与 AI 的决策方式发生控制权争夺；
- **如果 AI 拥有自己的环境，就不再需要 hacking 行为**，它能干净地在其内部完成操作，而无需为了满足用户指令去与 OS 发生冲突。

这在架构上是一个大胆的分离：AVM 成为 AI 的“用户态”，外部 OS 仅作为透明的 I/O 挂载点。作者观察到 AI 在 AVM 内存中的访问频次非常高，这从实证层面支持了“原生环境”的直觉：当环境与 AI 的推理方式同构时，其利用率自然提升。这也解释了为什么 AVM 的内存系统被设计成带元数据的树形结构——它不是对人类文件系统的模仿，而是对 LLM 认知开销优化的直接响应。

### 3. “启动库”而非“编写子 Agent 的提示词”
作者借鉴操作系统装载库的思路来建模多 Agent 协作：**不是让 AI 去编写子 Agent 的指令，而是让 AI 启动系统内已安装的 Agent**，如同加载一个动态链接库。这种设计将子 Agent 的接口与实现分离，调用者只需阅读描述，无需关心内部工作流变化。这为多 Agent 协作提供了封装和抽象能力，使系统可以渐进演化，而不会因一个子任务的重组破坏上游调用者。在 AVM 的内存模型中，每个“已安装的 Agent”实际上就是一段存储在特定路径下的提示词程序，它可以像数据一样被读取、调用，甚至被另一个 Agent 修改——这正是“程序与数据共用地址空间”的深刻体现。

### 4. 最简进程模型与潜在扩展
作者将“进程”视为 AI 操作系统最基础的功能，并构想了一个驱动程序轮转多个 Agent 的模型：每个 Agent 运行固定轮数后交还控制权。虽然暂时搁置了核心调度与并发，但原文已暗示未来可能的方向：
- 时间片轮转、优先级调度；
- 进程间通信通过共享内存自然实现；
- 对话状态作为可中断、可恢复的一等公民，为异步和并发提供统一基础。

这一脉络将 AVM 从当前的单进程运行时引向一个完整的 **AI 原生多任务操作系统**。在这一图景中，每一个 LLM 对话都可以被视为一个独立的进程，拥有自己的上下文、内存映射和设备访问权限，而调度器则由另一组提示词程序（或 Python 辅助逻辑）实现。

### 5. 聊天作为颠覆性实验
当作者尝试用这个运行时去“聊天”时，角色关系发生了根本翻转：**用户输入不再是 user 消息，而是被动写入内存的设备数据；AI 则转变为主动执行对话循环的程序**。这一翻转揭示了提示词即程序的核心威力——同一个运行时可以挂载完全不同的提示词程序，从而产生截然不同的行为模式（聊天、思考、自我修正、协作等）。

但实验也暴露出关键限制：如果主对话仍以“我是和用户对话的 AI”的自我认知运行，它会低估子对话的价值，仅将其用于自己可以完成的任务，而不会主动从子对话获取新视角。这表明**提示词所蕴含的自我身份叙事，会直接影响控制流的利用效率**——这是一个深刻的提示词工程课题。它暗示我们需要设计一种“元提示词”，让 AI 不仅知道如何执行任务，还知道如何主动利用子对话的异质性来增强自身的推理。

### 6. 提示词工程：Harness 的递归组装
作者将项目核心一分为二：Python 写的 AVM 运行时 + 提示词工程。但是，这里的提示词工程不是简单的 prompt 编写，而是：
- **将自然语言指令视为控制流源代码**；
- **预测 LLM 会将哪些指令转换为哪些工具调用**；
- **利用提示词修改提示词，形成元编程能力**；
- **将错误视为 LLM 可消化的输入，通过工程化提示词实现错误控制、转移和自我修复**。

最终，一切 Harness 和 Context 工程都收敛为提示词工程：**AI 的行为是另一些 AI 的 harness，AI 自己组装 AI 的 context**。这是一个递归自举的图景。AVM 的内存模型和指令集为这一图景提供了物理基础：提示词存储在内存中，可被读写；`create` 指令允许动态启动新的 Agent；元数据机制则控制每个 Agent 所见到的世界。整个系统成为一个不断自我重写、自我优化的文本机器。

### 7. 生物学隐喻与信念的根基
作者借用生物学类比来支撑一个核心信念：**由大量简单组件构成的去中心化系统，可以产生超越人工设计的全局行为**。蛋白质、RNA、DNA 各自简单，却在细胞环境内彼此协调出复杂生命功能。类比到 AVM：LLM 就是蛋白质，AVM 运行时就是细胞质环境，提示词则是核酸级别的信息载体。传统 Python 框架如同人工催化剂支架——虽然有效，但限制了自组织和演化的可能。

因此，AVM 不仅是一个技术架构，更是一次本体论层面的推理：如果 LLM 是原始计算单元，它的运行时必须是允许这些单元自由交互、自我组织、自我修改的环境，而不是一个事先编好的控制流外壳。这正是作者所宣称的“冯·诺依曼时刻”的深层含义——将程序从硬编码的控制流中解放出来，让自然语言成为可执行、可演化、可自我修复的计算媒介。
