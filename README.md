# AVM — 以 LLM 推理为原始计算单元的运行时

AVM 是一个运行时：以 LLM 推理为最小可调度计算单元，程序以自然语言（提示词）或 Python 代码的形式存放在内存中，由 AVM 负责调度和执行。

AVM 不是 Agent 框架。它不预设编排模式，不提供业务提示词，不与操作系统、硬件或网络直接交互。它提供一套指令集、一个内存系统、一个调度器、一个设备接口，以及把三者组合成"系统镜像"的格式。AVM 自成体系，有自己的内存模型和计算调度模型。

术语以 [CONTEXT.md](CONTEXT.md) 为准，本文档只在使用含义明确的地方简述。

## 计算模型

### 对话循环

对话（Conversation）是最小可调度执行单元。它由一个 Settingup 程序（提示词文本，或 type=`python` 的代码节点）和一条启动用户消息组成，循环执行：

1. 执行器推理一次（LLM 调用，或 Python 执行器调用）；
2. 输出为文本、工具调用，或两者都有；
3. 有工具调用时，Core 执行指令，把每个工具响应加入该对话的输入批次（batch）；
4. 返回不含工具调用的结果时，当前交互结束，对话进入休眠。

工具响应、被投递进来的用户消息、以及对话自己附加的用户内容，都会在下一次推理前合并进消息列表。

### 调度状态

对话处于三种调度状态之一：

- **活跃（Active）**：正在执行推理。同时只有一个活跃对话。
- **休眠（Dormant）**：主动挂起，等待事件或再次被调用。
- **就绪（Ready）**：等待被调度的队列。

"finished" 是概念态：记录被 `close_conversation` 内核级关闭的对话（个体结束）。Core 的调度状态机只有活跃、休眠、就绪三态。

### 排队调度与核心中断

调度采用排队模型：

- 被唤醒的对话进入就绪队列**末尾**（`call_service`、`send_instruction`、`return_result` 唤醒发起者等）；
- `create_sub` 是唯一例外：亚对话前插，立即执行；
- 亚对话完成唤醒父对话时直接激活（同一调用链）。

为防止单个对话占用过多执行权，每轮激活有指令预算（`instruction_budget`，默认 50，镜像 `meta` 可配）。Core 在**工具返回加入批次之后**检查预算：达到预算就中断当前对话，把它放回就绪队列末尾，让出执行权。预算按调用链继承：亚对话与父对话共享同一预算（`is_sub` 且 parent 匹配），`create_cmd` 创建的子对话有独立预算。调用链断开（选中了另一个无关对话）时预算重新计数。

### 交互结束与个体结束

"对话结束"有两种含义，必须区分：

- **交互结束**：对话返回不含指令的结果，当前一轮执行完毕。对话个体依然存在，可被再次唤醒（服务再次调用、事件回调等）。交互结束进入休眠。
- **个体结束**：对话被内核级关闭指令 `close_conversation` 关闭（可由对话自身或其他对话调用，不需要对方回应）。关闭后不可再调度、不可再被调用，记录为 finished；其服务注销、PLM 状态释放、未完成调用清理。

## 指令集

Core 只执行指令，不做业务决策。全部指令如下：

| 指令 | 作用 | 关键参数 |
|---|---|---|
| `memory_read` | 读取内存，返回给 LLM 的表示 | `ref` |
| `memory_write` | 写入内存 | `ref`, `content` |
| `memory_make` | 创建新内存地址 | `ref`, `key`, `mem_type`(str/dict/list) |
| `edit_metadata` | 编辑节点的 ctrl 元数据：set 写入 / get 读取（key 省略返回整个 ctrl）/ del 删除 | `ref`, `type`(set/get/del), `key`?, `value`? |
| `create_cmd` | 创建子对话（`system_ref` 必须指向 settingup 或 python 程序节点；只创建，返回 cid；子对话休眠等待指令；本对话保持活跃） | `system_ref`, `para_ref` |
| `create_sub` | 创建亚对话（立即执行；完成自动写回并唤醒父） | `system_ref`, `user_ref`, `para_ref` |
| `register_service` | 将当前对话注册为服务 | `name`, `what`, `needs`, `returns` |
| `call_service` | 调用已注册服务，等待返回 | `service_name`, `input`, `return_mode`(tool/message) |
| `transfer_service` | 移交控制权给服务，自身休眠，不等待返回 | `service_name`, `input` |
| `return_result` | 将结论按 ICC id 显式返回给发起者，并确保它成为下一个被激活的对话 | `content`, `icc_id` |
| `send_instruction` | 按 cid 向对话投递指令（支持多播） | `cid`(int/列表), `content`, `wait`, `return_mode`, `format` |
| `close_conversation` | 内核级关闭：关闭指定 cid 的对话（自身或他人，不需要对方回应）；关闭后不可再调度、不可再被调用 | `cid` |

## 内存模型

内存是全局共享的键值树，路径形如 `$MEM.a.b.c`。三种数据类型：

- **str**：叶子节点，直接返回内容。
- **MetaDict / MetaList**：带双元数据的复合类型。
- **设备（device）**：挂载到路径上的伪节点（见下文）。

### 双元数据

MetaDict / MetaList 有两份元数据：

- 元数据一（`meta`，字符串）：给 LLM 快速扫描的文件摘要/描述。LLM 读取时默认只看到摘要和键列表，深入索引后才返回子节点。
- 元数据二（`ctrl`，`dict[str,str]`）：给 Core / 内核态的结构化控制信息，如 `type="para"`（模型参数）、`type="settingup"`（LLM 提示词程序）、`type="python"`（Python 程序）。

### 字符串与链接

**str 永远是 str**：字符串值不会被当作引用解引用。`$` 递归解引用与 `&` 单层解引用是已废弃的设计，不存在于当前代码中。

**链接（Link）是设备**（设计已定，未实现）：把真实路径挂载为别名，如 `$rooms` → `$MEM.game.map.rooms`。对话通过链接访问目标内容，但看不到真实路径，因此无法借链接访问兄弟节点——这是 capability 边界的实现方式。读取时跟随目标；链接成环报错。

### 设备

设备是 `avm.memory_device.MemoryDevice` 的子类，通过接口与对话交互：

- `to_llm_string()`：LLM 读取该设备时看到的表示；
- `resolve_path(path)`：子路径访问（可选，默认抛错）；
- `set_value(value)`：写入（可选）。

Core 内置只读信息设备：`$MEM.conversations`（对话列表与单对话详情）、`$MEM.scheduler`（活跃/就绪/休眠与预算）、`$MEM.icc`（待处理 ICC 记录）、`$MEM.memory`（内存树摘要）、`$MEM.monitor`（监测帧摘要）。镜像可挂载自己的设备，例如 `$inputs`、`$outputs`（见[系统镜像](#系统镜像与快速开始)）。

## 对话间通信

### ICC 记录

每次对话间调用（`call_service`、`send_instruction`）由 Core 记录一条通信记录：

```
icc_id → { caller_cid, caller_call_id, mode, group_key? }
```

`icc_id` 就是发起者那次工具调用的 `call_id`。`return_result` 必须携带 `icc_id`，Core 按记录把结论路由回发起者；无记录即错误（输出到 stderr）。

### 消息格式（v2）

投递的消息是 JSON 格式字符串（默认；`format` 参数预留未来格式，目前只有 json），包含：

```json
{ "from": "发起者身份", "to": "目标身份", "icc_id": "...", "content": "指令内容" }
```

`from` / `to` 由 Core 按对话身份填写，不是 AI 自己写的。content 不强制 JSON。名字见下文。

### 返回方式

支持两种返回方式（`return_mode`）：

- **工具返回（默认）**：`return_result` 的结论作为工具响应，挂到发起者原调用的 `call_id` 上，发起者被唤醒并排到就绪队列末尾。
- **消息返回**：结论作为用户消息投递给发起者（`from`/`to`/`icc_id`/`content`）；发起者的那次工具调用先收到一条确认响应以满足"一次工具调用一次返回"的协议约束。

多播（`send_instruction` 的 cid 为列表）时，每个目标有一条独立 ICC 记录（`call_id#i`）；工具返回模式会等所有目标返回后，把各条结果按 cid 和名字合并成一条 JSON 数组工具响应，方便 Python 程序 `json.loads` 解读。

**父对话不是默认接收者**：创建关系不构成返回通道。子对话是否返回由它自己通过 `return_result` 决定；AI 的思考不默认透露给其他 AI。

### 名字与 cid

- 名字来自 Settingup 节点的 `name` 字段（是节点数据，不是元信息）。名字不唯一，冲突时用文件地址消歧。
- 带名字的对话必然有 Settingup 文件；亚对话（直接传提示词）没有名字，其身份 = 父对话身份 + 亚对话 cid。
- `send_instruction` 只用 cid 寻址。名字 ↔ cid 转换是内核职责（工具未实现）。

## Python 程序

Python 程序与 LLM 对话对等：都是 AVM 中的一等执行单元，通过 OpenAI 兼容的消息格式交互（输入 messages 列表，输出 `content` + `tool_calls`）。

内存节点 `ctrl.type="python"` 声明 Python 程序，`content` 是代码。`para` 的 `model` 参数选择 PLM（Python Language Model）类型：

| model | 行为 |
|---|---|
| `plm.simple` | 计算器：单行表达式求值。受限命名空间（安全 builtins + math），无状态。 |
| `plm.python` | 图灵完备：Jupyter 笔记本式语义。系统消息与用户消息都执行进同一个持久命名空间（跨轮次保留）；多个 print 全部执行，输出按顺序拼接为整体返回。 |

Python 对话的 `model` 必须是注册表（`PLM_REGISTRY`）中的名字，否则报错，不静默回退到 LLM。

### 确定性

Python 程序输出是确定性的：执行器通过比较上一次输入与本次输入，只处理新增的消息；只有最后一条消息的返回被保留（对同样的输入序列，只有同样的输出）。消息带 `icc_id` 时，具体 PLM 自动构造 `return_result` 返回（工具调用构造是具体 PLM 实现的行为，基类不保证）；工具调用 id 是对消息内容做确定性哈希。

### 沙箱

PLM 代码运行在受限环境：安全 builtins 白名单 + AST 检查（禁止 import、禁止双下划线属性访问、禁止危险调用名如 open/eval/exec）。它防止 Python 程序访问宿主系统（文件、网络、进程、时钟、熵源）；AVM 内部行为不受限。真正强隔离（子进程 + OS 级隔离）超出 VM 范围。

## 系统镜像与快速开始

一个 JSON 文件 + 若干设备 Python 文件 = 一个标准 AVM 系统镜像。规范见 [docs/system-image.md](docs/system-image.md)，要点：

- **显式节点**：内存每个节点都是 `{ "kind": "str"|"dict"|"list"|"device", "meta"?, "ctrl"?, "value" }`，无任何隐式转换（str 也必须显式包装）。`kind="device"` 是任意层级都可出现的可读性标记，实际挂载在 `devices` 段。
- **para**：`ctrl.type="para"` 的 dict 节点存放模型调用参数（`model`、`temperature`、`use_tool`、`extra_body`、`reasoning_effort` 等），均以字符串存储，数值型加载时自动转回。
- **devices**：数组，每项 `{ path, file, class, args }`。`file` 是相对镜像文件的 Python 模块路径，`class` 是其中的设备类，**必须继承** `MemoryDevice`，否则加载报错。这样"一个 JSON + 几个定义设备的 Python 文件"就是一个完整的系统镜像。
- **init**：启动对话配置（`name` 默认 `"init"`，`system`/`system_ref`、`user`/`user_ref`）。只启动 0 号对话，不预置其他对话；服务由对话运行期自己注册。
- **persist_to**：运行结束后内存写回路径（异常也写）。
- **meta**：`version` 必须为 1；`instruction_budget` 可配核心中断预算。

```bash
pip install openai python-dotenv pytest
echo "OPENAI_API_KEY=sk-..." > .env

python -m pytest                          # 全部测试（MockLMU，不调真实 API）
python main.py                            # 从 debug.json 读取镜像配置并运行
python main.py <image.json> --frames      # 运行后打印监测帧摘要（stderr）
python main.py <image.json> --transcript api.txt  # API 调用全文落盘
```

调试参数写在 `debug.json`（`image` / `frames` / `transcript`），不需要改命令行（VSCode 固定运行 `python main.py`）。示例镜像见 `images/demo.json`、`images/calc_driver.json`。

## 调试与观测

### 监测器（Monitor）

每轮对话推进结束后生成一帧（Frame），第 0 帧为基线。帧内容：

- `lmu`：最近一次执行的结果（`result`）、思维链内容（`reasoning`，与 result 同截断策略）、工具调用摘要（`tool_calls`）、耗时、错误；
- `sched`：活跃 cid、就绪队列、休眠队列、下一个 cid；
- `conversations`：每个对话的状态、消息条数、输入批次内容。

提供 `trail()`（单变量跨帧轨迹）、`diff()`（两帧间变化）、`find()`（按谓词找帧）等查询；`--transcript` 把每次 API 调用全文写入文件。

### 思维链内容

LLM 响应中的 `reasoning_content`（思维链）被完整存入对话历史，并在后续请求中随 assistant 消息回传（无值则空字符串）——这是厂商协议的硬性要求，也是"回传所有推理内容"的既定策略。监测器记录它（与普通内容相同的截断策略）；`$MEM` 信息设备不暴露它（外泄控制靠禁止内部访问，不靠不记录）。

### 错误输出

工具调用参数 JSON 解析失败、未知工具名等错误输出到 stderr，面向运行者，不喂回给 LLM 让它自纠。整体错误处理机制仍在设计中（见[当前状态](#当前状态)）。

## 决策与动机

这个项目没有先例，以下按推理过程记录每个设计选择的目的，而不是先给结论。

### 控制流放在提示词里

现有框架用 Python 写控制流，LLM 只是被调用的函数；改一种协作模式就要改程序。提示词是文本，存放在内存中，可以被对话自身读写和修改——这提供了元编程和错误修复的物理基础。AVM 的选择不是"提示词还是代码"，而是控制流存放在哪一层。

### 对话作为进程

线性上下文随轮数增长，回溯早期推论需要翻越长历史，信号衰减。进程树隔离上下文：每个对话有干净的任务边界，父只看子结论，深度增加不增加回溯成本。这是把操作系统的进程概念映射到 LLM 运行时。

### 子对话与亚对话的唤醒差别

两类协作的紧耦合程度不同。亚对话是父的控制延伸，父需要它继续，所以完成即唤醒、结果自动写回。子对话是独立执行单元，只对 AVM 整体内存的目的负责；父创建子后进入休眠、等指令，子完成不构成父的唤醒事件。父要恢复，靠 `return_result` 投递的消息（直接唤醒）或注册的事件。

### str 永远是 str，链接是设备

如果字符串值可能被当作引用解引用，存储内容和读取结果就不一致，间接层不可控。链接是显式设备：别名挂载、子路径委托、成环检测，同时承担能力边界——对话只拿到别名，拿不到真实路径，就不能访问兄弟节点。

### 返回用显式工具

LLM API 规定一次工具调用必须有一次返回。如果结论回传依赖"对话恰好以正确形式自然结束"，结果不确定：LLM 总是输出内容，但不一定输出工具。`return_result` 把返回变成显式动作，由子对话决定返回或不返回。调用后子对话收到确认，下一轮以无工具结果收尾进入休眠，调用者成为下一个被激活的对话。

### 交互结束进入休眠

交互结束不等于个体失效：对话个体保留，之后可被再次调用或事件唤醒。终态设为休眠与异步调度一致——挂起的调用者不在可运行队列里，事件到来才回到就绪。

### 错误面向运行者

调试期系统错误需要人看见；LLM 自纠会掩盖运行时缺陷。工具参数解析失败、未知工具名输出到 stderr，不喂回 LLM。

### 镜像格式显式

镜像要精确复现系统状态。隐式转换（"JSON 自动转成内存类型"）省事但不可控：类型、元数据、para 的识别都靠猜。显式节点（kind/meta/ctrl/value）让镜像每个字段有确定含义，代价是冗长。调试程序值得这个代价。

### 内存用双元数据

LLM 上下文有限，大文件不能整体塞入。元数据一给 LLM 快速扫描（描述 + 键列表），深入访问才展开子节点；元数据二给 Core / 内核态（type、signature），控制程序如何被解释。这是控制 LLM 视野的手段。

### 排队调度与核心中断

对话之间的相互通信是主要负载，每次通信都产生类似 await 的让出行为，因此排队调度（唤醒进队尾）足够公平。`create_sub` 前插是因为亚对话被父启动时直接激活。核心中断放在工具返回加入批次之后检查，保证中断时状态完整可恢复；读写内存不是阻塞行为，阻塞性设备通过事件机制（设计中）通知对话。

### 预算按调用链继承

亚对话被视为父对话的延伸（启动即激活），如果每次激活都重置预算，递归循环调用可以无限延续；同链共享预算限制了这一点。`create_cmd` 子对话是独立个体，预算独立。

### ICC 与消息格式

结论返回到哪个对话必须可寻址，所以每条调用都有 ICC 记录，`icc_id` 由 Core 保证（发起者工具调用的 call_id）。父对话不是默认接收者——AI 的思考不默认透露给其他 AI，创建关系不构成返回通道。`from`/`to` 由 Core 填身份，AI 不需要也不应该伪造。

### 思维链内容回传

带 tools 参数的 thinking 模式请求必须原样回传 `reasoning_content`，否则厂商返回 400。AVM 把它存入历史、总是回传（无值空字符串）；监测器记录它用于调试。思维链等价于传统代码的调试输出，但它是 AI 的思考内容，不暴露给其他对话。

## 如何设计 AVM 程序

（本节是设计导引，用户后续会在此修改。）

### 程序放在内存里

一个程序由两部分组成：

- **Settingup 节点**：`content` 是程序文本（提示词，或 type=`python` 的代码）。节点的 `name` 字段是对话的身份。
- **para 节点**：`model`、`temperature`、`use_tool` 等调用参数。

对话由 `system_ref` 指向的程序节点（或入口对话的字面量）和一条用户消息启动。`create_cmd` / `create_sub` 的 `system_ref` 必须指向 `ctrl.type="settingup"` 或 `"python"` 的程序节点，指向 str 节点或无类型节点会报错。程序文本在内存中，对话可以读取、检查、修改其他节点——AVM 的元编程基础在这里。

### 一个对话做一件小事

每个对话只承担一个微小、可管理、可追溯的任务。从概率模型角度：模型倾向认可自己刚产出的内容（否则不会写），而另一个模型看到旧内容倾向质疑（否则不会被派来）。小的任务边界是隔离这两类偏差的物理手段；对话之间的结论靠显式消息传递，不靠共享上下文。

### 用指令表达控制流

对话不直接"执行"，只做两件事：输出文本（结果）或调用工具（指令）。Core 执行指令并把响应放回批次。控制流是提示词里写好的循环协议：读输入 → 处理 → 调用工具 → 读返回 → 写输出。行为边界靠提示词约束，不靠代码强制。

### 选择调用关系

按三个维度选：

| 需求 | 用 | 说明 |
|---|---|---|
| 创建独立执行单元，之后按需发指令 | `create_cmd` | 父不休眠；子休眠等指令；返回靠 `return_result` |
| 立刻执行一件小事并要结果 | `create_sub` | 父休眠；亚对话完成自动写回唤醒父 |
| 复用已注册的既有对话 | `call_service` | 调用者休眠等待返回 |
| 移交控制权，不等待 | `transfer_service` | 适用于无限循环/尾递归 |
| 给已有 cid 的对话发消息 | `send_instruction` | 支持多播与两种返回方式 |

### 记住返回通道不是默认的

创建关系不构成返回通道。想让对方返回，指令消息里带上 `icc_id`（工具调用的 call_id 就是），对方在返回时回填。其他对话要知道结果，靠信号事件（设计中）。

### 消息是字符串

投递的消息就是 JSON 格式字符串：`from`/`to`/`icc_id`/`content`。Python 程序用 `json.loads` 解析；LLM 用提示词约束自己从中取字段。不要发明自己的信封结构——字段就是这些。

### 确定性

Python 程序对同样的输入序列只有同样的输出；非最后一条消息的返回被忽略。LLM 程序没有这种保证，提示词要写清楚分支和终止条件，避免无限循环（预算中断会强制让出，但那是兜底不是常规路径）。

### 预算意识

一轮激活内的工具调用计入调用链预算（默认 50）。一个循环协议里别堆太多工具调用；达到预算会被中断并排到队尾。

### 用监测器调试

每轮推进都有帧：活跃/就绪/休眠、工具调用摘要、结果、思维链、错误。`--frames` 打印摘要，`--transcript` 落盘全文；信息设备让对话也能查询调度状态。
